# Changelog

## 0.6.1 (2026-10-30)

rabbitbrain.ai opens for everyone, every view says one wording, and the record says what rb saw happen and what it recorded afterwards.

- **rabbitbrain.ai is open.** `rb login` and `rb sync` work for anyone who signs up. `rb sync --with-record` names the code where the repository's origin is an https address, with any credentials taken out, so a reader who reruns a shared record gets the code with it; otherwise it names none and says so. Plain `rb sync` names no repository.
- **One rule for the code's address.** `rb export` and `rb sync` name the code only at an https address a reader can fetch, with credentials, query and fragment taken out, and otherwise say in one line that the bundle names none (`data.repo_unnamed`).
- **What rb saw, and what it recorded afterwards.** Each run, analysis, call and finding says whether rb saw it as it happened or recorded it afterwards (`witness` in `rb status --json`). One line says it for the record, on the page, in `rb open`, `rb status`, `rb context` and `rb ui`: "Kept with rb since 2026-10-28. 2 runs and 1 call were recorded afterwards, not as they happened." (the page and `rb open` write the day as 28 Oct 2026), in place of "Recorded since ..., what came before it is Retrospective". A run recorded afterwards says so in the Runs table and on its card, and a finding counts the runs it rests on that were.
- **One wording in every view.** `rb status`, `rb context` and `rb ui` say "Rules: 1 met · 1 can't tell yet", and `rb status` and `rb context` say "Needs judgment", as the page does (`rb open` says "Needs your judgment"). Commands, flags, `--json` keys and MCP tool names are unchanged. History, the cards and the model name a run, an analysis and a call the same way: an analysis with no title reads by its experiment and the minute it was recorded (`analyses.{id}.named`).
- **Words.** `rb freeze` says a rule a session declared is locked now; `rb confirm` names the notes a design leaves not confirmed, in `--json` too; `rb log` and a setting's history say each op in words; a cited value that differs is said where it is set, by the CLI and the SDK alike; a miss with a call proposed on it says the call waits.
- **Reconcile carries the command.** The `rb run add` line `rb reconcile` proposes for a file a watched command wrote carries that command, so the run's command reads as observed. A recipe tells runs with the same label apart.
- **The rerun prompt says what the bundle holds:** whether it names the code, and whether it holds the record.
- **Sources read again.** `rb open` and `rb sync --watch` read each source again at each look, and `rb ui` notices a source rewritten with as many bytes.
- **Windows** (still a preview, [#2](https://github.com/rabbit-brain/rb/issues/2)): a clone counts its changes from its record's commit, however late git dates it; the code's address is said with `/`, with git's own error rather than a fragment of its advice; rb's generators write UTF-8 on any terminal.
- The README and the manual lead with `pip install rabbit-brain`.
- rb no longer infers a provider for Gemini CLI, which it does not detect.

## 0.6.0 (2026-10-28)

The record is plain YAML in `.rb/`, `rb reconcile` compiles what the repository already says, every write records who made it, and every finding is read on its axes.

- **Research overview with detail on demand.** The exported page and local browser open on compact inquiry summaries. Tabs separate the work's views, and findings, experiment matrices and provenance expand when requested. A deep link opens the corresponding tab and record. Exported pages remain self-contained and work offline.
- **Select the evidence and declare its units.** Criteria can select shared and per-arm per-run settings. Fixed design factors report cell coverage and ranges instead of sampling intervals across design choices. A merge that brings a declared unit to the arms it separates reads as an integrity problem (`unit_separates_arms`), with the repair in `rb status`. Explicit reversal relationships show both comparisons, their alignment and uncertainty, and travel with question decision snapshots.
- **Each inquiry reads its own evidence.** Criteria can be filed directly to questions with `rb criterion add -q <question>` or `rb criterion file <criterion> <question> --why "..."`. An optional `--when-met "..."` keeps the author's interpretation of a met rule, with attribution and its own declaration time. Question readings separate direct evidence, descendants and unassigned criteria; missed rules never imply the inverse, and integrity problems prevent an interpretation from becoming active. New question calls keep that scope and become outdated when its evidence, interpretation or integrity changes, without being moved by unrelated results in a shared experiment, rb's own wording or a move of the question. In a record where no criterion is linked to a question or related to another criterion yet, a question call is made on every criterion filed under the question and the questions below it. Revisions and withdrawals keep their history, frozen changes require an amendment, and clones inherit the structure without the parent's calls or evidence. Two branches that file one criterion to one question, or relate one pair, merge into a record that reads with neither declaration active (`question_link_ambiguous`, `relation_ambiguous`), and one filing or relation repairs it. rb's own next steps, items and guides link each criterion they offer to its question (`-q`), and once any criterion is linked or related, `rb status` gives the agent `unassigned_criterion` for each criterion filed under a question and linked to none, with the filing that links it. CLI, Python and MCP share the same operations, and `state.relations(<criterion>)` reads a criterion's relations in Python as `rb show` reads them.
- **A question's counts are its linked criteria.** In `questions[].rollup`, `rules`, `results` and the criteria in `untested` count only the criteria linked to that question (`-q`, `rb criterion file`), so a criterion only filed under it, or linked to a question below it, no longer counts there; `experiments`, `children`, `open_children` and the planned experiments in `untested` still count the work filed under it and below it, and `rb status` says the two apart as `linked here` and `below it`.
- **Retitle a project.** `rb project title "<new title>" --why "<reason>"` changes the title while keeping the project's identity, evidence and calls. The log keeps the old and new titles, who changed it, why, and any words passed with `--words`. The same write is available as `state.set_project_title(...)` in Python and `project_title` over MCP.
- **Optional usage analytics.** Off until `rb telemetry enable`. Limited, inspectable PostHog events measure operations and research-record milestones across the CLI, SDK, MCP, TUI and local web viewer. No research content or command arguments are sent. `rb telemetry preview` shows pending events; `rb telemetry disable` removes local analytics state. UI polling, tutorials and CI do not count as engagement. See [PRIVACY.md](PRIVACY.md).
- **Prebuilt wheels** for Linux x86_64 and aarch64, macOS Intel and Apple Silicon, and Windows x86_64. Each wheel carries the executable, SDK and TUI; installing one needs no Rust compiler.
- **Many branches and worktrees, one question.** Agents fork worktrees and branches freely; the record is built for it. Whatever is added to an experiment is a file of its own (`variants/<name>.yaml`, `notes/<id>.yaml`, `criteria/<id>.yaml`, beside `runs/` and `analyses/`; the project's notes in `.rb/notes/`), so parallel work merges without a conflict; an experiment kept the earlier way (variants and notes in `experiment.yaml`, criteria in one `criteria.yaml`) reads as it is and moves on rb's next write to it. A comparison counts a run while the arms it compares are as they were: a variant added on another branch, or an ablation added afterwards, does not move other arms' runs to an earlier spec. A record git merged from two sides rb wrote is rb's own when both sides are kept, and named (`merged_outside_rb`, with adoption first) when the merge dropped one; an adoption takes an author from either side and never a forged one. Ids carry six random characters; two branches that mint one id are named (`id_collision`), and `rb doctor --restore` gives the second record its own. Every run keeps the git tree of its code under `refs/rb/snapshots/`, so squashing or deleting a branch does not lose the code a receipt names. The journal lives in the clone's shared git directory by worktree, so what a removed worktree's commands printed is still found. `rb status` says what is elsewhere: for each other worktree and unmerged branch, what it adds to the record. Branches and worktrees are context on a run's receipt, never the record's structure.
- **A worktree's runs keep its own code.** A git worktree nested in the checkout, with no record of its own, writes to the checkout's record, and a run's or an analysis's receipt and `rb journal run` take the worktree's commit, branch, uncommitted changes and exact code; `rb journal run` runs the command there. Every write from a linked worktree keeps its path (`worktree`, in the data alone). Other worktrees nested in a checkout are not its code, nor files its journal watches, and a submodule moved on is not a large file. A clone that lacks a run's tree says so. rb's reads leave git's index as it was. In a nested worktree, `rb status` and `rb context` say once where it writes. A worktree outside the checkout with no record is told where the project's record is and how to bring it here, and `rb init` there needs `--new-project`. `rb status` names each place elsewhere by its branch and path, says when a worktree was removed since, and tells a separate project apart. A worktree name git gives again no longer shares the earlier worktree's journal, and a moved worktree keeps its own.
- **See every worktree from your own screen.** `rb open` says which place it shows, by its branch and path, and its Where and Version pickers show another worktree's record or a past version of the record (a commit that changed `.rb/`, by its commit and time), read only: nothing is written there, and a call that waits there shows the one command that confirms it. A past version is read from a checkout rb keeps in its own folder of the clone while the screen is open, and takes away when it stops. `rb ui` says the same and `w` switches; `y`, `n` and `c` act only where it started. A run recorded in another worktree says where, and a finding that counts one says so once. Each place is named in short, by its branch and its path from the main checkout or from `~`, with the whole path on hover, and a file inside a nested worktree by its path there. While another place or a past version is shown, a bar says so in words, with the way back, and the address keeps the place, the version and the tab, so a reload, Back and a bookmark show them again. Where a run was recorded links to that place, the home lists the other places with their own counts and the calls that wait there, and where a reading's runs ran other code, rb says which, from their receipts (a page by commit alone). Nothing is summed across places, and `rb page` and `rb export` carry none of these labels: a file inside a nested worktree is named there by its path inside it, as in another worktree.
- **rb asks before it changes a file that was there.** `rb init` makes the agents' instruction files that are not there. An `AGENTS.md` or `.mcp.json` that was there changes only once you agree: in your own terminal rb asks once, showing exactly what it would add, and No is the default; `--yes` answers up front for a script. Anywhere else rb leaves the file as it is and says what to add and the one command that adds it. An edit keeps every byte that was there, in the file's own line endings and indentation: `.mcp.json` is never reformatted. A skill or Cursor rule at rb's path that rb did not write stays as it is. `rb skill add` (`--agents-md`, `--claude --project`, `--cursor`) and `rb reconcile --apply` (now with `--no-agents`) follow the same rule.
- **Leaving rb.** `rb init --dry-run` lists every file and integration `rb init` would write, every file that was there it would change and how, and what later commands add, writing nothing; a write a link takes elsewhere is named with the file it lands in, and one outside the repository waits for your yes. rb keeps an ownership ledger of every write it makes outside `.rb/` (`<git common dir>/rb/owned.jsonl`): the instruction files it installs, what it adds to a file that was there, with the file's sha256 before and after, its pages and exports, the refs that keep a run's code and its own folders. `rb page --out` and `rb export --zip --out` never write over a file rb did not write, nor rb's page, export or export folder once someone changed it or added a file to it: such a file is refused and left as it is, unless `--replace`. `rb remove` takes rb out of a checkout, and only what its ownership ledger says rb wrote there, as rb wrote it (rb's text a teammate committed stays): it shows the plan first (what it will remove and how it knows each is rb's, what it will keep and why, what is not rb's to touch), says when the record holds writes no commit keeps, names what git's index holds staged of rb's with the command that unstages it, and asks once in your terminal (`--yes` elsewhere; `--dry-run` removes nothing). It never deletes a git object, a worktree, history or a research file, and it is refused where `rb confirm` is. A removal stopped midway is finished by running it again. A round-trip test holds it: after `rb init`, an afternoon's work and `rb remove`, every file with its time, the refs, the objects git reaches, git status, HOME and TMPDIR are as they were before rb, but for directory times and the objects only rb's refs reached, which rb names and leaves for git's gc.
- **rb is one program, on Linux, macOS and Windows.** `pip install rabbit-brain` brings `rb` as a compiled binary, with the Python package beside it for the SDK (`import rabbit_brain`) and the terminal screen (`rb ui`), which ask that binary for everything: the command line, MCP, the SDK and the screen read and write through the same code. It reads YAML, JSON and TOML configs itself and asks git each question once per command. On Windows paths are written with `/`, in the record and in what rb prints, and a path typed with `\` is the same path; a watched command (`rb journal run`) writes to a pipe there, not to a terminal of its own. A record made on one system reads on another: `.rb/.gitattributes` tells git to leave the record's files as rb wrote them, and where git converts line endings (Git for Windows does by default) a text file checked out with `\r\n` is the file rb recorded with `\n`, so a setting's source, a run's files and an indexed folder do not read as changed.
- **Every failure is said one way.** `rb <command>: <what happened>`, then a line that says what to do (a command line that does not parse shows the usage first); with `--json`, the same in `errors[]`. When the system under rb is what failed, rb's sentence names the file or the address and carries the system's own words for why (`Could not write shared/page.html: Permission denied`, with the directory to check). A fault in rb's own code is `E_INTERNAL`, exit 3, and asks to be reported; so is an install that cannot run a part of rb (the screen without its Python), which says what to install. Every other failure exits 2, and a tour that stops exits as the step that stopped it. Where there need be no failure there is none: `rb page --out` makes the directory it is asked for, `rb journal` passes over an entry it cannot read and counts it, `rb init` starts the record when an agent's instruction file cannot take rb's section (it says which, and leaves the file as it is), and `rb logout` removes the credential here whatever stops the revoke. A credentials file that is not one holds no credential for `rb sync`; `rb logout` says it cannot look in it, and leaves it as it is. A port out of range (`rb open --port`), a hub address that is not one and an argument that is not UTF-8 text are usage errors; `rb clone` says a bundle path that is not there as a missing file, and what is wrong with a bundle it fetched of the address it was given; a missing credential names the hub that was asked; an address that answers, and not as the hub does, is said as that. `rb show <file>` gives a file of an odd shape its problems, field by field. Over MCP, params a method does not take are `-32602` with a sentence, and a tool's arguments are an object. Rabbit Brain YAML refuses a number too large to hold (`1.0e+999`).
- Versions before 0.6 were a different tool; their commands and records are not carried forward.
- **The agent contract.** `bench/agent/` is the executable definition of an rb-compatible agent: a spec of nine invariants (record the moment that mattered, skip the chatter, keep the user's words verbatim, never manufacture a finding, reconcile before finishing, notice a failed check, use the grammar, cite files, start honestly where the work already is) and nine cases, each a synthetic repository with rb installed the way a user installs it, a short session, and checks read from what the agent left in `.rb/` and what it said. `python bench/agent/run.py` plays them with scripted agents; `--agent-cmd` plays them with a real one, behind a counting `rb`. CI holds the contract to account: the ideal agent passes every check, and each careless agent fails exactly the checks it is written to fail.
- **The grammar: the same work, recorded the same way.** A rerun for variance is another run; a changed hyperparameter, a variant; an ablation, a variant with role ablation; an invalid run, a new run that replaces it (`rb run add ... --replaces <run> --why "..."`, which retracts the old one, keeps it on record and links the two); a different approach, a new experiment that `follows_from` the old. In SKILL.md, AGENTS.md and the contract.
- **`rb journal run` reads what a command reports of itself.** The output passes through as it comes (a pty in a terminal; with `--json`, on standard error so the envelope is alone on standard output). A last line `{"metrics": {...}}` is kept with the command, and `rb reconcile` proposes the run that records it, with the command, when it ran and the code it ran with, once an experiment reads those names; `rb journal run` says which run it proposes, or why none. A failed command keeps its last ten lines, and a failing check shows them.
- **rb_delta: what changed since you last looked.** In an agent session every command on the record ends with the facts the session must not silently forget, each told once: results not recorded, folders not compiled or changed, failed checks and audits, moved manifests, stale decisions, calls made on a failing line, edits outside rb, and what the user or another session wrote, each with what it changed, its reason and the user's words. In `--json` and over MCP as `rb_delta`, where a write's `by` says who made it; in text under `Since this session last looked:`. It never says what research to do.
- **`rb init` sets up the agents it finds.** The skill and rb's MCP server in `.mcp.json` for Claude Code, rb's marked section in `AGENTS.md` for Codex and the agents that read it, a rule for Cursor: found from the repository's own instruction files, added beside what is there, said line by line; `--no-agents` leaves them alone. It says when `.gitignore` keeps a file it installs out of git. Run inside an agent session it installs nothing, since that session would load none of it, and names the commands for later sessions. It ends with the one line to paste into the agent's chat, the same line the README, `rb ui` and llms.txt give: `Use Rabbit Brain to track this: read rb context, then record where the work stands.`
- **Starting the record in a project already under way.** `rb docs --start` (the MCP resource `rb://start`) prints a short start protocol for a session joining work already done: it asks the researcher nothing up front, takes the current frontier as its scope (the question actively worked on, with the experiments, runs, findings and open calls around it), inferred from the session's context and the files and never asserted, records it first with each rule linked to the question its comparison answers (comparisons that share an arm in one experiment), checks memory by rules rb reads, reads runs from their stores, takes criteria only from documents (a criterion whose reason is a file and line alone is refused when that line does not state its threshold; a direction rule only where a document states the direction), records a dated decision a committed file states as a past call that waits for one confirmation and no call from memory, and ends with a report that says what it took as the frontier and why, points at what waits, and ends with no question. While the record holds no question in a repository with history (a commit beyond a new repository's README, license and ignore files, a results folder or a database), `rb status` and `rb context` point at it (`no_question`); so do `E_NO_PROJECT`, and `rb compile` and `rb reconcile` with no record. The agent contract gains a `brownfield` case with its acceptance checks.
- **The exact code behind a run.** A run recorded or watched with uncommitted changes keeps the git tree of the files as they were: a digest anyone with the same files computes, written through a temporary index (the user's index, branch and files untouched) and kept under `refs/rb/snapshots/` as a ref to the tree, with no commit and nothing in `git log --all`. `rb show <run>` gives the diff; `rb run add --tree` records the code of a run made earlier.
- **`rb reconcile` compiles what the repository already says.** Coding agents leave research in the repository: results folders with a README, a manifest of the source hashes that made them, analysis and audit files, large arrays kept out of git, audit scripts and tests, a reproduction guide, a commit. `rb reconcile` reads it against the record, experiment by experiment. Each results folder with a report is an experiment that points at its files by path and hash, with what git does with each; nothing is copied. A results folder a recorded run named (`--from`, `--config`, `--artifact`) is read by that run's experiment, and a new number in it that rb saw land after its first look here, or one a command under `rb journal run` printed, is proposed as another run of that experiment (a file already there, or one a checkout brought, is listed and never proposed), with each per-run value its own config beside it (passed as `--config`) or the line of the one command that wrote it gives, and a line that would need a value neither gives, or one they give apart, is never run by `--apply`; a folder of results files alone that nothing reads is listed as unplaced, never made an experiment (many such folders are one counted line, and the MCP tools keep the first 100 of each long list unless asked for all), and a file in it that rb saw land after its first look here is proposed as a run where exactly one experiment's criteria read its numbers. The next step rb suggests names `rb reconcile --apply` only while it would add no experiment, and work from before the record began points at `rb docs --start`. Its reports' title, opening lines and the sections their own headings call results, limitations and next steps are quoted verbatim with file and line, and so are the commands of the reproduction guide they link. A manifest's hashes are checked against the code as it is now; an audit file is read for what it says of itself; the repository's own checks (`audit_*`, `test_*`, `check_*`, `verify_*`) are registered with the command the repository gives for them, their outcome read from the last run rb watched; and each folder says whether it is clean enough to checkpoint. `rb reconcile --apply` keeps it in the record as whoever runs it, records the runs it placed without doubt, and logs one line saying what changed in the research, which `rb status` prints. From then on every read checks the repository as it stands: `reindex`, `unindexed_folder`, `manifest_changed` (the `stale` gate), `audit_failed` and `check_failed` (a new `checks` gate). A decision on an indexed experiment is made on what its repository said and reads as made on an earlier reading when that changes, and a call that moves a line on while its own audit or check says failed is shown to the user (`call_on_failed_check`). A results folder's numbers go only to the experiment that reads the folder, never to another on a metric name. rb chooses spans by the files' own headings and words nothing itself. It needs no record to start: in a repository with no `.rb/`, `rb reconcile` reads it all the same and writes nothing, and `--apply` starts the record at the repository's root, titled as its README titles itself.
- **A session's reading reads as not confirmed.** A note a session wrote (`rb note add`, or a run's `--note`), and an interpretation a session declared (`--when-met`), read as not confirmed on every screen and in rb's text (`· not confirmed`, `declared when met, not confirmed`, `Recorded interpretation · not confirmed`), naming no writer; who wrote it and the session stay in the JSON, the log, MCP and the SDK.
- **A note's words show beside it.** The words given with `rb note add --words` show beside the note on rb status, rb context, rb show, rb open and rb ui, as words given (the user's own when they gave them in their terminal), never on a page, and under `words` on each note in `rb status --json` and `rb context --json`. So do the words given with `rb experiment gate --words`, beside the gate, and under `gate_words` on the experiment.
- **One comparison, one number.** Where a criterion reads a variant against the baseline otherwise than the experiment table's unpaired means (paired by unit, or over runs a `--where` selects), rb compare, the page and rb open show that criterion's reading in the cell, never a change of their own; `rb compare --json` gives it as `read_by`, with `unpaired` saying what the means are over.
- **A call is the user's.** A call recorded in an agent session (`rb decide`, the SDK's `decide`, MCP's `decide`) is proposed, not made: questions, experiments, criteria and settings read as if it were not there, and `rb status` and `rb context` list it apart from the calls (**Proposed, not made**), with its subject, action, reason as given and the one command that confirms it; `rb open` and `rb ui` show it in a quiet group of its own, and a page lists it as rb status does. The user confirms it with one command in their own terminal, `rb confirm <id>` (`--all` says each call, then confirms them all; alone it lists what waits), or `c` on `rb ui`: the same call, recorded as theirs, with its log line naming what it confirms, so the record's format does not change; its reason still reads as the session's note on it. `rb confirm` in an agent session is refused, and a write where a session left its id or entry point (`CLAUDE_CODE_SESSION_ID` with `CLAUDECODE` unset) is that session's, as `rb confirm` reads it. `rb decide --past [--when "..."]` records a call made before it was recorded, Retrospective and dated as given; from an agent session it is a past call mentioned, not confirmed, until one `rb confirm`, whoever ran `rb init` and whatever document it cites, since a session cannot attest the past it reconstructs. With `--source <file>[:<line>] --quote "..."` rb checks the document and says what it found beside the call, in `rb confirm`, `rb show` and `authority.basis`: the quote is in that file and line, committed on a day before the record began, or why rb cannot tell. Until it is confirmed, a past call reads in the file's voice: the document's words verbatim with its file and line, and the reason a session gave only as a note on it, never as the user's call; a past park or stop says which runs of its experiment were produced after the day it gives (`runs_after`). `rb confirm --all` leaves a subject more than one call waits on to `rb confirm <id>`, and `rb confirm` says what the call is made on now. Words given in an agent session read as `words (as given): "..."` on every surface, never as the user's, until the user confirms the call they came with. Each decision carries its computed `authority` in `--json`, over MCP and in the SDK; `rb status` gives `pending` beside `decisions`, and the open items `call_proposed` and `past_call_unconfirmed`.
- **An experiment's design waits for you.** Its design is what it records of how it tests its question: its questions, hypothesis or purpose, why, variants, what it varies, settings with their sources, criteria and their interpretations, gate and freeze. One a session wrote any part of says `design not confirmed` once on its own views (`rb show <exp>`, its pane and row on `rb open`, its card on `rb ui`, its part of a page), with the one command that confirms it, and `why: not recorded` or `hypothesis or purpose: not recorded` where it has none; `rb status`, `rb context` and a page's summary say every such design in one line. `rb confirm` lists each part by part, and `rb confirm <exp>@<hash>` confirms it as listed, with its gate, in your own terminal only: one log line that changes no file. The listing, and the line under what waits on `rb status`, end with the one command that confirms all of it as listed, by id and hash, in place of `rb confirm --all`, which confirms what reads when it runs. Its standing is read from the log alone, by a snapshot rule: it reads confirmed only while it is exactly a design you own, one you confirmed or one your own write made from a design you owned then (an adoption only where rb is sure what its files held before), which that write's line keeps (`detail.owned`: a hash over rb's structured form of the parts, so a later rb that words a part otherwise reopens nothing). A session's later change reopens it, said part by part with what each was and is now against the closest design you own; your own changes to a confirmed design keep it confirmed. Once a session touched a design it waits for one confirmation, even after you rewrite what it wrote, and a merge, a clone, an older rb or a clock can only make rb ask again. A gate waits with its design while a session wrote a branch or its words as they read now, in a session's voice until it reads as in a design you own, your branch or words beside them included; once you confirm it, it stays yours until a session changes it, and the interpretations a session gave its criteria wait again once a session changes a design you confirmed. A design that waits in a record waits in its clone (`rb clone`), until you confirm it there. Confirming changes no finding or reading. Where something a session wrote can wait for you, every screen draws a character a terminal would hide as its escape, as `rb confirm` lists it, and `--json` keeps the text as written. `design` on each experiment, `designs_pending` and `counts.design_pending_count` in `--json`. An older rb lists the confirmation of a design with no gate in `rb log` as a gate line.
- **Preview a write.** `rb run add`, `rb spec set`, `rb criterion add`, `rb decide` and the 21 other write commands AGENTS.md lists take `--dry-run` (`dry_run` on the same tools over MCP and the same writes in the SDK, where it returns a `DryRun`). rb makes every check the write makes and exits as it would, with its refusal or its warnings, and writes nothing: no record file, no log line, no cache, no lock file, no git object, ref or index. It changes no file's time, though a clean filter the repository gives git, such as Git LFS's, runs as it does on any read. It says what the write would write, each record file with its content and the log's new lines (`data.would_write`), and its text names no writer. A check that fails leaves no mark when it is previewed. A preview reads the record as it stands, so a write that rests on one not yet made is previewed after it. The bulk writes preview in their plain form, as before: `rb reconcile` without `--apply`, `rb doctor` without `--restore` or `--adopt`, `rb fmt --check`.
- **Source checks read numbers and names as files write them.** Digit separators are part of the number: `48_200`, and LaTeX's `48{,}200` and `48\,200`, state 48200 as `48,200` does, never 48 or 200. A name LaTeX and Markdown escape (`seq\_len`) names `seq_len`, in a source check and in `rb compile`.
- **A row of a SQLite database is a run, read where it is.** `rb run add <exp> --from results.db --table evals --where precision=int8,seed=1` reads exactly one row of a database, told by its first bytes whatever its name: its columns that name a declared metric are the run's numbers (`--select` narrows them), and `--set seed=@seed` and `--produced-at @finished_at` take a per-run value and the time the run was made from its columns (a database's own times never date a row). No row, or several, is refused with how many and the first of them, and nothing is written. The receipt keeps `row`: the database's path and sha256, the table, the row's key and rowid, and the column each value came from; reading the same row again records nothing, however the database has grown, the same row read in a second experiment is warned of at the write and listed by `rb status` (`row_in_several_experiments`), naming both, and a row whose values changed since is refused, with `--replaces` or `--again` as the way on. After the spec changes, `--replaces <run> --why "..."` reads the same row or file again under the spec as it is now, with the same receipt; `rb spec set` and `rb spec vary` point at it, and so does the warning on the same row given again without it. The database is opened read-only and never written, with no -wal, -shm or journal file made beside it; one that cannot be read without writing (writes still in its -wal, an unfinished write in its journal) is refused. `rb compile` lists a database's tables, their columns and row counts, and the columns that name a declared metric. `exp.record_from(...)` in Python and `run_add` over MCP read a file or a row as `rb run add --from` does. A setting is verified from one column of one row as from a file's key (`--source results.db#configs[config_id=c1].width`), and `--set seed=@configs.seed` reads a per-run value from the row of another table that holds what the run's row holds in the column they share, the receipt naming that row. SQLite is built into rb.
- **What a run rests on, said as such.** A command given for a run made before it was recorded reads as a command given later, not observed, unless `rb journal run` watched it make the numbers or `--command-source <file>:<line>` cites a log line written by then that holds it; `rb run add` says so, `command.given` says how rb knows in `--json`, and `rb status` counts such runs (`command_later`). A file written after its run, an export, reads as `file written <date>, after the run`, never as the run's own output (`file_written_after`). `rb show` and `rb page` say when a run was produced, as reported, beside when it was recorded, and the repository's state as the state when it was recorded; the page's receipt is lines, not a stored dict. `rb status`, `rb context`, a page, `rb open` and `rb ui` say in one quiet line when the record began, after how many of its runs, and that what came before it is Retrospective. Words an agent writes about its own writing are pointed out and counted (`writer_words`), never refused. An experiment's late criteria are one item, which asks for no run where none is expected.
- **The next experiment carries the decision it gates.** `rb experiment add --if-holds "..." --if-not "..."` (`if_holds` and `if_not` over MCP and in the SDK) keeps what happens either way, in its author's words, and `rb experiment gate` sets or revises it later, the earlier words kept in the log. `rb status` reads as the state of the research under each question: the hypothesis and the gate of what is planned, what the files say of what ran, each experiment's latest note, and the calls made on the work with the user's words. `rb show`, `rb context`, `rb open` and `rb page` show the gate too.
- **Findings are read on axes, never in one word.** A criterion is a rule over one comparison (subject, reference, metric, estimand) with a role (primary, secondary, exploratory, gate). Its finding says, computed on every read: the comparison with its interval and units; the result (gain, loss, unresolved, equivalent, point only, measured); whether the rule meets, misses, is undetermined or untested; the timing (declared before the evidence, after it, after the data was seen, or in an order nobody knows); how many independent units it rests on; every integrity problem with what it depends on; the latest decision on it and whether it was made on the reading as it stands; and the readings it replaced. The headline is `rule · result` (`criterion met · loss`, `gate missed · point only`). rb reads the runs itself: a paired difference per unit, averaged within units, then over units, with a Student t interval from 3 units (Welch when the arms never share a unit). Thresholds read the estimate (`--at-most`, `--at-least`, `--equals`; `--each` for every unit, `--bound` for the interval's bound); `--better`, `--noninferior M` and `--equivalent M` read the interval. A missed gate is a priority call, never a refutation.
- **Units, not rows.** Runs with the same per-run values are one unit; `population.unit` names the setting that defines units (2 photographs with 4 noise cases each are 2 units); `--repeats <run>` records a check of a run, averaged with it. `--min-n` counts units. A run's identity is its provenance: the same output files are one run; equal numbers from two executions are two runs.
- **Analyses.** `rb analysis add <exp> --compare "a/b:m@estimand=est[lo,hi]" --method --unit --units --reads --input --source` records a computation over saved outputs and the comparisons it produced, checked against the document that states them. An analysis that reports a comparison is read in place of the runs, and rb's own reading stays as history; a corrected one `--supersedes` the old with a reason, and every earlier reading stays on record. What an analysis rests on is traced every step back, and one that counts more units than the runs it read form (by the declared unit) is an integrity problem.
- **Timing and exposure.** A criterion is declared when it is written, by whoever wrote it. Its timing compares that with when its evidence existed (`--produced-at`, the journal, git, the file's time, or the record time, and it says which) and with when its evaluation data was seen (`rb resource expose`, or another experiment evaluating on the same resource). Evidence it could have been fitted to counts even after a spec change. `late` fails when a primary criterion is not shown to precede what it reads.
- **Decisions.** A decision (`rb decide <subject> accept|reject|investigate|continue|park|stop|pivot|ship --why --revisit`) records the reading of every finding it was made on; when a reading moves, or a new one appears under it, it says it was made on an earlier reading.
- **rb tracks who did what.** rb never refuses a write because of who makes it. Freezing, amending, deciding (accept, reject, investigate, continue, park, stop, pivot, ship), vouching for a setting, retracting anything and `rb doctor --adopt` work for anyone and are recorded as whoever made them; a call recorded in an agent session waits for the user's confirmation (above). Attribution is the integrity: every write records who made it (`human:<name>` or `agent:<name>`), the chat session when the runtime exports one (on every log.jsonl line, on decisions, on run receipts), and the reason as given (`--why`); inside a detected agent session `RB_ACTOR=human:<name>` is ignored, so the record shows who actually did what. When an agent acts on the user's words from the chat, it passes them verbatim with `--words "..."` (on every command that takes `-m`/`--why`, and on `question add`, `experiment add` and `note add`; `words` in MCP tools and in the SDK's `decide`, `retract` and `freeze`): they are kept beside the reason on decisions, freezes, amendments, retractions and criteria, and on the log line, and shown as `your words: "..."` once they are the user's (above). Nothing is paraphrased. `rb status` items carry `who` as a hint of who usually acts, not a permission: calls on results and on lines of work (undecided, gate missed, decision outdated, investigating) are the user's, setting items the agent's, and drift, changed cited sources and state from a newer rb anyone's; an agent records a call when the user asks for it, with their words.
- **Which agent made each write, and on which model.** An agent's write records `agent` on its log line and, for a run or an analysis, on its receipt: its name, its version (from `AI_AGENT` or the MCP client's `clientInfo.version`), its provider (as it said it, else inferred for Claude Code on Anthropic's own API, Codex and Gemini CLI) and its model, only as it said it: `rb context --model <id>` (or the context tool's `model`) for the rest of its session, or `RB_MODEL` for one command. With no session id rb keeps no model. A session's agent facts get one `session` line in the log, for each writer and channel in it, when they are first known or change; it records no write, and rb versions before it read past it. `rb_delta` says once how to give the model while none is recorded, `rb context` says it in every briefing until one is, and `--json` gives the actor with `agent`. Cursor's agent (`CURSOR_AGENT=1`, its chat in `CURSOR_CONVERSATION_ID`) and Codex known only by its thread or session id are recorded as agents. A human's write keeps a session only when `RB_SESSION` names one, so a Cursor terminal's trace id is no longer taken for a chat. An adoption can no longer change a receipt's actor, `actor_via`, `via`, session or `agent`, nor the `via` beside who wrote a record.
- **Who made a write is in the data, not in rb's words.** rb's text and every sentence it builds name no writer, a human or an agent, so a missing name never marks an agent's write: a call reads as made, when and why (`accepted 2026-10-10: within budget`), a criterion as declared before or after its evidence, a line of `rb log` as what changed. No session id, channel or detection source is in them either, and no branch or worktree is named as a write's: `rb status` names each place elsewhere by its branch and path, as rb names a place in the labels it computes for one; what a command printed in a worktree removed since is found as such, with no worktree's name. The record and the fields of `--json`, MCP and the SDK keep all of it; `rb doctor` still says how this shell's writes are recorded.
- **Publishing the record is a choice.** `rb export` and `rb sync` publish the page alone, with a manifest hashing it: no record, no file a check reads, no `bundle.zip` and no Reproduce panel with `rb clone`. `--with-record` (`with_record` in the SDK's `export` and the MCP `export` tool) carries the record too, as the bundle rb wrote before, and rb says then what the record keeps: who made each write, an agent's chat session, name, version, provider and model, the user's words passed with `--words`, and each run's host, platform and branch; the bundle's README says it too. `--url` takes `--with-record`, since there is nothing to clone without it; `rb clone` of a page alone says it was exported without the flag; `--json` says which was written (`with_record`).
- **No screen names a writer either.** The page `rb page`, `rb export` and `rb sync` write, `rb open` (with the `/state.json` and `/card.json` its tab draws, where each field that kept who wrote now holds `""`, whatever the record keeps there) and `rb ui` name no writer, session, channel, agent or branch, and use no word for a role: runs have no "recorded by" column, a relation's declarations print what has a value, "For your agent" is the Next step, and what is not the user's call is "still open in the record" (`open in the record · N` on `rb ui`, whose `a` key opens that list). `rb ui` counts what was written since the user last looked, whoever wrote it (`Since you last looked: 3 writes, 2 runs recorded · last <day>`), and nothing before their first look, and its `y` prompt says what a yes records, not as whom. The user's words show on `rb open` and `rb ui` without the `your words:` tag, and never on a page, which anyone may be sent; nor does a page show the platform a run's receipt keeps, which `rb open` shows. The screen refuses an agent session as `rb ui` does when it is started with `python -m rabbit_brain.tui` too.
- **Plain record text.** rb shows the text anyone writes exactly as written, on every screen, so the manual and the contract `rb compile` prints ask for plain text (a statement lifted from a report keeps its words and drops its markup): Unicode symbols (≥, ×, Δ, σ, ∼) instead of LaTeX, a macro's name spelled out, no citation keys or table and figure references, and no name of the agent or tool that did the work. After an agent's write whose new text holds LaTeX, rb says so in one line that names the field and what to write instead: after the write's text, among `data.warnings` in `--json` and over MCP, and as a `rabbit_brain.RBWarning` from the SDK, which now also warns of what `rb run add` and `rb analysis add` warn of beside a write (an input whose copy here changed, numbers typed with no document, numbers that differ from the run already recorded with the same output files). The user's words, quotes of files and commands as given are never flagged, nor is a price, a path, a shell or Make variable, a regex or a code span; a human's writes get none, and rb never refuses or changes the text.
- **A project is titled for the work's theme.** `rb init "<the work's theme>"` names what the work shares (a paper's title, a model, a line of work), and each inquiry is a top-level question with the experiments that answer it. rb init's help and the next steps it prints (`rb question add`, then `rb experiment add -q`), `rb status` on an empty record, `rb context`, `rb compile`, the `E_NO_PROJECT` fix, the tour, the skill and the docs say so.
- **Questions are a tree.** `rb question add --parent`, `rb question move`, and an experiment filed under several questions (`-q q1 -q q2`, `rb experiment file`); a question's state comes from the decisions on it, and its roll-up counts the findings linked to it by rule and by result, and the sub-questions and planned experiments below it.
- **Integrity is local and forged authority is none.** A record changed outside rb is an integrity problem of the findings that depend on it, and only those; the rest keep their readings. A decision rb did not write is nobody's call, and an adoption can never change who wrote or decided something (`E_ADOPT_AUTHORITY`); a run deleted outside rb is named by the findings it fed; `rb show` of an edited record says what changed.
- **The record is plain YAML in `.rb/`, one file per record.** `.rb/project.yaml` and `notes/`; `questions/<id>.yaml`; `experiments/<id>/experiment.yaml` with a file per variant, note and criterion under `variants/`, `notes/` and `criteria/`, per run under `runs/` and per analysis under `analyses/`; `metrics/`, `resources/`, `decisions/`; `log.jsonl`; and, local and gitignored, `cache/`. Every file opens with `rb: 1` and then its `kind`. The files keep to a strict subset of YAML, Rabbit Brain YAML (mappings, lists, strings, numbers, booleans, null, comments; no anchors, aliases, tags or merge keys; a value YAML 1.1 and 1.2 read differently must be quoted), read and written by rb's own parser, fuzzed against PyYAML. Comments survive rb's rewrites, and a comment or a reformat is not an edit: tamper detection compares each record's content hash. `rb fmt [--check]` writes the canonical form; `rb show <file>.yaml --json` gives canonical JSON and the hashes log.jsonl records.
- **One vocabulary, everywhere.** The record's words are project, question, experiment, variant, setting, criterion, run, analysis, comparison, result, resource, metric, finding, decision, note and relation: the same words in the files, the JSON Schema, the CLI, MCP, the SDK, the docs and every screen. A hypothesis is what an experiment tests, and a direction nothing has run yet is a planned experiment; an assumption is a note.
- **The format is a published contract.** `rb schema all` prints format 1 as one JSON Schema, committed as `schema/rb-v1.schema.json` (its `$id` is https://rabbitbrain.ai/schema/rb-v1.schema.json), with a test that fails when it drifts from what rb enforces.
- **Resources: identity, location and availability are separate.** `rb resource add <id> --type dataset --name "..." [--version --file --sha256 --digest --at PROVIDER:REF --url --recipe]` records what a dataset, checkpoint, code or artifact is and where its bytes have been (local, url, git, W&B, S3, GCS, Hugging Face, RunPod); `rb resource locate` adds a place. Availability is computed on every read: present, changed (a copy is here, not the bytes named), remote, reconstructible, lost. Identity is as exact as what was recorded, and says so: exact (a hash or digest), version, or name only. Deleting a 100 GB copy never loses what the benchmark was.
- **A run pins what it touched.** `rb run add --input RES[:ROLE] --output RES[:ROLE] --host provider=runpod` records, per resource, where it stood and the bytes of the copy here when the run was recorded; a copy whose bytes differ from the resource's identity is recorded as found, with a warning. Every experiment says what a rerun would need and where each piece stands (code, environment, machine, resources, files), and a dataset that changed after the runs read it is named as such.
- **Experiments carry their story.** Purpose, hypothesis and why; notes, verbatim with their writer; relations to other experiments, shown from both sides; a computed state (planned, open, or what the latest decision made it: accepted, rejected, investigating, parked, stopped, pivoted, shipped). Experiments, runs, analyses and resources carry global uids.
- **`rb status` answers where the record stands on its own**: the questions and their findings, then what needs a human and what an agent can do (each item saying who usually acts), what the experiments depend on, what ran (and whether every receipt is what rb wrote), and the project's notes. A long list in `rb status` or `rb context` names its first or latest ones and counts the rest, with the command that lists every one, so thousands of results folders or hundreds of runs keep the first screen readable; `--json` keeps every item. In the user's own terminal, the Next line names `rb confirm` first while a call waits on them. Its first line says the project's title once where the title is the project's id, and a count of two reads as both (`after both its runs were made`, `both units`), of one as the only one, never `all 2`. A test cuts the network and removes any account, then runs status, show, compare, context, log, doctor, env check, fmt, schema, page, export, reconcile and clone: none of them may need rabbitbrain.ai.
- **`rb open` only reads**: every POST gets 405, and there is no launch key. What rb found in the repository and nobody recorded shows as facts, not requests: under "Your call" in `rb ui` and `rb page`, under "Found in the repository" in `rb open`, beside how many calls wait on you, which `rb status` lists under Needs a human. The list of the calls waiting on you, on `rb open` and the page, names each one once, by what it asks and the title of what it is on, linked to the deepest question that lists it, so it holds as many as the count says.
- **Bundles are `rb-bundle` version 2** (the record inside is `.rb/`, format 1). A bundle's page is computed from the bundle itself, carries the documents its analyses were checked against, and `rb export --with-record` names the resources it leaves behind and says what the record it carries keeps, which anyone who can read the bundle can read. A clone keeps each setting's source (verification is redone here with `rb spec verify`), gives every experiment a new uid and a `reproduces` relation to the parent's, and keeps resources' identities while leaving another machine's paths behind. A bundle holds at most 512 MB, zipped or unpacked: `rb export` refuses one that would hold more, naming its largest parts, and `rb clone` one that does, and what `rb clone`, `rb export` and `rb sync` have half made is taken away when Ctrl-C, SIGTERM or SIGHUP stops them; a clone keeps its parent's address without the credentials, query or fragment it was fetched with, and a published fork's page links the parent only at a web address.
- **rb never publishes.** rb and rabbitbrain.ai are like git and a code host. `rb publish` fails with `E_NOT_AVAILABLE` and says what to use. `rb export` writes the page you can host anywhere, and with `--with-record` a bundle that `rb clone` reads; `rb login` and `rb sync` are an optional bridge to the site, where sync puts a private copy of the page (and of the record with `--with-record`) in the user's account and making it public happens on the site, from the record's page. The hosted service is not open yet: until it is, `rb login` and `rb sync` addressed to rabbitbrain.ai say so (`E_NOT_AVAILABLE`), send nothing, and name what works without it (`rb page`, `rb open`, `rb export --with-record`); a hub named with `--hub` or `RB_HUB_URL` is still called. `rb --help` groups the commands to match: "Calls" (freeze, decide, retract), "Carrying it" (export, clone, env), and "rabbitbrain.ai (not yet available)" (login, logout, sync) last.
- **Agents are told when to record.** The MCP server's instructions say to record when the research state materially changes (a question or hypothesis introduced, revised or dropped; an experiment or control proposed or run; evidence that changes a conclusion; a baseline, variant or metric established; an important uncertainty; the next experiment or a decision chosen) and not implementation chatter, to point at the repository's own files rather than copying their prose, and that `rb reconcile` finds results that landed unrecorded. The packaged skill (`rb skill`) says the same in about fifty lines and defers to `rb docs` for the rest.
- **Where rb looks, said where it reads.** `rb status`, `rb context`, `rb open`, `rb ui` and the page say where rb looks on its own (`out/`, `outputs/`, `results/`, `eval-out/`, `metrics/` and any folder a recorded run named, the files in the repository's top folder, and the .json, .yaml and .toml files git shows as new or changed), when it last looked, that it reads what code, configs, docs and database rows say only where the record points to them, and that it sees only the commands run through `rb journal run`; `rb reconcile` reads the same list. Where git's folder cannot be written (an agent's sandbox can keep it read-only while the project stays writable), the journal and the ownership ledger are kept beside the record in `.rb/` and that line says so; the first look that can write git's folder moves them there.
- **Changes nothing in the record cites.** A .json, .yaml or .toml file outside the results folders rb reads that changed since the record's start, or since the last `rb reconcile --apply` in the user's own name, and that no setting, run, analysis, criterion, call, resource or indexed folder cites, is listed by `rb reconcile` by path with the commit the count starts at, and counted in one line on `rb status`, `rb context` and the user's screens (`uncited_changes` in `--json`). rb says what changed and that nothing cites it, never whether it matters. `rb reconcile --apply` keeps their paths on its line, so they are recorded while their bytes are those.
- **Recovering what nobody recorded, honestly.** `rb reconcile` says where it looked, never proposes a file of progress numbers as a run, nor one that was there when `rb init` first looked (that is the work the record began after), moved or copied from it, or put back from git by a stash or a restore (a result rb saw land keeps that look through a stash or a checkout, and is still proposed), and the journal shows when a file was last written, not only when rb saw it. `rb compile` lists files matched by metric name as candidates with when each was written, never as a deterministic fact.
- **`rb tour` runs on a clean install** and in the loop's order: the criteria are declared and frozen before the runs write their outputs.
- **Fail closed, in more places.** A record file only a newer rb reads is named and never read, written over or restored, and this rb writes nothing while one exists; so is a declared relation of a kind or orientation only a newer rb knows, while the rest of its record still reads, and `rb clone` refuses a bundle that holds either rather than leave it behind; an unreadable criteria file stops its criteria with `E_STATE_CORRUPT` instead of hiding them; a second copy of a record in another file is caught as written outside rb, set aside by `rb doctor --restore`, and never adoptable; retracting an experiment keeps its criteria in every gate, and `rb status` gives each of them the one repair it takes (`experiment_retracted`: `rb retract <criterion>`), never a command that writes to the retracted experiment.
- **A hand edit is named as one.** Format 1 is fixed: a later rb that adds a field writes a new format, which an older rb reads as needing an upgrade. A field or value rb does not know, in a file that is not what rb last wrote, is said as edited by hand or written by a newer rb (still `E_STATE_NEWER`), naming the file, a part's own where an experiment is read with it, and the fix offers `rb doctor --restore` beside the upgrade where rb holds its last write; `rb doctor` says the same, once, `rb open` draws the fix under the message (`fix` beside `error`), and `rb ui` gives the terminal back and says both.
- **A misspelled metric is named, not refused.** `rb criterion add` with a `--metric` that no run or analysis reports and the catalogue does not hold, close to a name one of them does (`change.val_los` beside `val_loss`), says so in one warning line naming that name (`data.warnings`, and an RBWarning from the SDK's `criterion()`); the criterion is declared as given, since its metric declares the name by use. Declared before any run, a run under the close name says the criterion likely misspells it, and `rb status` gives it the retraction as its step, never the misspelt name.
- **A run that counts toward nothing says so.** `rb run add` whose numbers no criterion of the experiment reads (a flat `{"val_loss": ...}` where the criteria read `fp32.val_loss` and `int8.val_loss`) records the run and says in one line that it counts toward nothing, with the names its criteria read and the shape a file gives them in, `{"fp32": {"val_loss": ...}, "int8": {"val_loss": ...}}`, or `--variant <name>` for one variant's numbers; the SDK's `run.log` says the same as an RBWarning. The README shows that shape.
- **After `uvx`, the way to keep going.** `rb tour` run by `uvx --from rabbit-brain` ends with how to run its next commands while `rb` is not on the path (`uvx --from rabbit-brain rb ui`, or `uv tool install rabbit-brain`), and the README says so after the `uvx` route.
- **Third-party notices ship with rb.** Each wheel, the sdist and the GitHub release carry `THIRD-PARTY-NOTICES`, the licenses of the crates built into the `rb` binary.
