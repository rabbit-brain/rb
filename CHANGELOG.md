# Changelog

## 0.5.0 (unreleased): the review, readable without the terminal
- `rb report <run> --open` writes `report.html` beside `report.md` and opens it. One self-contained file: the viewer's script and stylesheet are inlined and the comparison travels with it, because the file is opened from disk and `file://` blocks a fetch of a sibling. Nothing loads over the network and no part of the run is uploaded. `--html [PATH]` writes it without opening a browser, which is the form for CI and for an agent.
- Evidence images are referenced beside the file, so a run's sheets are not duplicated into every report. `--embed` carries them inside it instead, for a single file to attach to a pull request. A report written outside the run directory embeds them automatically, because the relative paths would not resolve there, and says so.
- It is the same viewer the website runs, given local data. **Two implementations of the same arithmetic, held together by a test:** `tests/test_conformance.py` runs the website's `lib/comparison.ts` and this package's `stability.py` over the same fixtures and fails on any difference, in a verdict, a count, a per-case label, the queue order, or a saved check's status or wording. Four divergences found on the way in, all of which would have shown a reader a different answer than `report.md`:
  - the viewer computed at generic limits rather than the run's own, so any project that changed a limit got a report that contradicted its receipt;
  - it did not implement `max_last_update` or `max_trajectory_regression` at all, and `rb init` sets the second one for every new project;
  - errors were rounded on the way in, which moves a case across the limit it sits on;
  - a saved check with a `max_reversals` limit was evaluated as if that limit were absent, and failing checks were left out of the verdict line.
- The generated report keeps nothing in browser storage. Every `file://` document shares one origin, so a report that restored the last saved workspace would open showing the previous run's cases under this run's title.
- A limit the run carries but this version cannot evaluate is stated in the report itself, as it already is in `report.md`. A policy that was stored but unchecked must not read as a policy that passed, in either file.

## 0.4.0 (2026-09-21): the workspace, and buying one without a sales call
- `rb plans`, `rb workspace status`, `rb workspace checkout` and `rb workspace push <run>`. Everything the tool already did stays free and local; what a subscription buys is that a finished review stops living only in the terminal that produced it.
- **A person completes every purchase.** `rb workspace checkout` returns a URL and stops. It cannot pay. The sequence for an agent whose push was refused is in `rb docs`: push gives `E_WORKSPACE_PAYMENT_REQUIRED` with the plan and its price, checkout gives a link to hand to a human, status is polled until active, then push again.
- The token is read from `RB_WORKSPACE_TOKEN` and nowhere else. It is never written to disk, never put in a URL, and never printed, including in errors, which a test pins. A CI secret is enough and there is no credential file to leak.
- No new dependency: the client is `urllib` from the standard library.
- Six error codes with fixes: `E_WORKSPACE_NO_TOKEN`, `E_WORKSPACE_AUTH`, `E_WORKSPACE_PAYMENT_REQUIRED`, `E_WORKSPACE_NOT_SELLABLE`, `E_WORKSPACE_UNREACHABLE` (exit 3, because the host being down is not the caller's mistake and the run is still on disk) and `E_WORKSPACE_REJECTED`.
- A plan that is published but unfinished cannot be bought: checkout returns `E_WORKSPACE_NOT_SELLABLE`. The team workspace is priced in the open and marked unsellable until it actually shares a review with a second person.
- **Corrected in `AGENTS.md`:** "Nothing leaves the machine" was no longer unconditionally true. It now reads that nothing leaves unless you send it, naming the two commands that do (`rb share` writes a file for a human to send; `rb workspace push` posts one comparison you name), and that no command sends anything on its own.


## 0.3.0 (2026-09-20): the stored contract is wider than the engine
- The data model was shaped by one task and one diagnostic, and a run's stored shape is the expensive thing to change once a team has history in it. This release widens the contract without touching the comparison logic, so runs recorded now do not need migrating later. Nothing here changes what is checked or how anything is ranked.
- `Metric.lower_is_better` is a real boolean, not `Literal[True]`. A higher-is-better measurement (depth `delta < 1.25`, task success, PSNR) can now be recorded faithfully. **The engine still only compares lower-is-better metrics**, and a bundle whose primary metric is higher-is-better is rejected at the boundary with a message saying so, because `error_outcome` calls candidate-minus-baseline a regression and would otherwise report every improvement as one.
- Each case carries `baseline_metrics` / `candidate_metrics`: secondary measurements on the same case, such as `latency_ms` or `memory_mb`, which a release decision needs alongside accuracy and which previously required a second comparison. They may be signed, unlike the primary error. `Bundle.metrics` records their definitions so a stored run is self-describing. This version stores and reports them; it does not rank or flag on them.
- Each case carries `baseline_series` / `candidate_series`: named per-iteration series beyond the single scalar trajectory. The scalar `*_trajectory` remains the one the stability statistics read.
- `Limits.extra` carries named limits this version does not enforce, so a run records a team's whole release policy rather than the part that happens to be implemented. `Limits.unenforced_limits()` lists them, and both `rb findings` and the report name them explicitly and say the verdict does not account for them. A limit that is stored but unchecked must never read as a limit that passed.
- **An unevaluated limit now fails the gate.** A human-readable warning is not enough: what decides a release is `--json` and the exit code. `rb check run` and `rb run` emit `policy: "complete" | "incomplete"` and `unenforced_limits`, and exit non-zero when a declared limit could not be evaluated, even if every saved check passed. A gate that could not assess a stated criterion has not passed it. No existing run is affected, since `Limits.extra` is new in this release and nothing sets it yet.
- Fixed in the same release, found by that acceptance test: `limits_from` rebuilt `Limits` field by field and dropped `extra`, so a stored unenforced limit silently vanished on every `check run` and `findings`. The field meant to stop something being silently dropped was itself being silently dropped.
- The README no longer says a model still moving at its last iteration is "unreliable on that case whatever its final number says". The measurement supports a correlation (Spearman 0.88 to 0.92 with per-case error across the four public checkpoints), not a categorical verdict, and `stability.py` now says the `unstable` label marks a case worth looking at rather than an answer known to be wrong.
- 19 tests pin these seams, including that the report stays quiet when every limit is enforced, speaks up when one is not, and that CI cannot go green on a policy it did not finish evaluating.


## 0.2.2 (2026-09-19): rb onboard
- `rb onboard`: the step before `rb init`, for a team that has not decided anything yet. `rb onboard` writes `brief.json` (project, task, architecture, framework, model code, checkpoints, how one case is stored, whether there is ground truth, iterations, an optional evaluator and metric override, and the decision the review has to support; `rb schema brief` prints the schema); `rb onboard --brief brief.json` writes `rb.toml`, `INTEGRATION.md` and, when no built-in adapter covers the architecture, `rb_adapter.py`: a scaffold that imports, that `rb doctor` loads, and whose unwritten parts each say what that method must return, with the brief's own case layout, label situation, metric and evaluator path written into the docstrings that need them. Deliberately not a working adapter, because nothing can guess a team's loader, valid mask or metric formula and a scaffold that returned plausible numbers would be the failure adapter agreement exists to catch. `INTEGRATION.md` carries the ladder with what each step proves: doctor, verify-hook, verify-adapter, a five-case run, the review; plus the one line to hand a coding agent, the three things a form cannot tell us, and an opt-in way to send a result back or ask for help.
- `rb.toml` now writes a `[metric]` section when the project names its own metric. `Config` accepted one and `render_config` never emitted it, so a team's own unit was silently replaced by the task default on the next load.
- A reversal is an iteration whose update grew by more than 5% over the previous one, which is a size and not a direction; the finding text said "reversed direction", which is the separate `sign_reversal_rate` statistic computed from the update fields. Every case's `why` now says "its update grew again N times", the report's convergence legend distinguishes the two, and a test pins it.
- README, `llms.txt` and the site say what the tool is for in the same words, name stereo and depth as in scope, and make the two arguments that were only in the manual: the adapter has to reproduce the model repository's own evaluation before a run reports anything, and findings that turn on a thin margin are marked borderline. `llms.txt` now carries what an agent must pass on to a human (the limits are heuristics, borderline cases may not reproduce, a failed or skipped adapter check comes first), because a summary that drops those is misleading.

## 0.2.1 (2026-09-19): adapter agreement, and borderline outcomes
- An adapter must reproduce the model repository's own evaluation before its results count. Adapters may state a reference path (`reference_value(model, case)`: the per-case error through the repository's own loader, forward call and metric formula, sharing no code with `infer` / `metric_value`); `rb verify-adapter --checkpoint <ckpt>` compares the two on a few cases, and `rb run` does the same on `[adapter] reference_cases` (default 5) per checkpoint before evaluating anything. Disagreement beyond 0.001 relative is `E_ADAPTER_DISAGREES` (exit 3) and the run writes nothing; `--skip-reference` runs anyway and the receipt says so. Every receipt now carries `adapter_agreement` (status, cases, largest difference, the reference path) and the report has an "Adapter agreement" line. The `raft` adapter's reference path is RAFT's `core/datasets.py` KITTI loader, `InputPadder`, `RAFT.forward(test_mode=True)` and the per-image EPE from `evaluate.py`; `torchvision` (RAFT's own requirement for that loader) joins the `[raft]` extra. The tests include an adapter with the bug class this exists for (the encoder fed the wrong input range: every number finite and plausible, none of them about the model) and check that it is refused.
- Environment failures (`E_ADAPTER_IMPORT`, `E_MODEL_CODE_MISSING`, `E_DEVICE`, `E_HOOK_*`, `E_INFERENCE_FAILED`, `E_ADAPTER_DISAGREES`, `E_EVIDENCE_DEPS`) now exit 3 as documented; they exited 2.
- From the first blind agent pilots (two coding agents given only the one-line prompt, one importing an evaluator's CSV of the real raft-things → raft-sintel review, one running the RAFT adapter on CPU), fixed the same day:
  - Wording: the `why` text no longer calls an over-limit current model "settled" ("The current model is not settled on this case either (35% late revision, 0 reversals)"), names only the limit that was exceeded, and never says "the error looks fine" for a case without ground truth.
  - The run files and the `--json` output are the same documents: `bundle.json`, `record.json` and `findings.json` write nulls explicitly (a parser written against `rb findings --json` no longer breaks on `findings.json`).
  - Architectures: `rb doctor` prints each checkpoint's sha256, architecture and parameter count and warns when the two differ; the receipt's checkpoint lines carry the architecture and the report adds a note that the review compares two models, not a retrain; `record.json` → `checkpoints.*.architecture`.
  - `rb import`: `--columns case_id=frame,...` maps an evaluator's own column names (no converter script); series cells may be `;`- or space-separated; a bad cell names the row and the column; `rb schema csv` prints a sample; `--note` goes into the receipt; the report's convergence table now appears for imported trajectories too; `rb case --render` on an imported run explains that rendering needs the model and the data instead of pointing at `rb init`, and is no longer suggested for such runs.
  - `rb findings`: the mean error line; the table labels `current`, `candidate`, `change`, `late`, `move`, `rev` with a footnote; `--sort candidate-error|current-error`; "no gt" instead of "n/a px".
  - `rb check save`: the default `max_error` is the better of the two models on the case plus `max_regression` (was the current model's, which let an improved case get 2.7x worse before the check fired); checks carry the unit, so `rb check list` no longer prints "units". `rb check run` prints the flagged cases and the check results (`--all` for every case) instead of 200 OK lines.
  - Receipts: the recorded command is shell-quoted so it pastes back; the report's Reproduce line includes every limit in force; the model-code line says when the checkout is not a git repository; `record.json` → `dataset.content_hash` hashes the input and ground-truth files themselves; `wall_seconds` covers the whole command, evidence included; `Notes:` line when a note was given.
  - `rb runs` lists each run with its models, case count and verdict. `next` hints repeat `--runs-dir` when one is set. `rb init` says what it did to `.gitignore` and which dataset name it chose; `alternate_corr` is in the written rb.toml.
  - Warnings raised by the model code (RAFT's autocast and meshgrid deprecations, four to seven lines per command) are counted in one stderr line and hidden unless `--verbose`.
  - AGENTS.md: an `rb import` worked example, the vocabulary note (`stable` is an error outcome, `unstable`/`settled` are trajectory words), verify both checkpoints, what `iterations` and `checks.json` assume stays fixed, what the two dataset hashes mean, and the architecture note in what to report.
- From the third pilot (an agent given a custom iterative model with its own evaluator and no adapter):
  - A custom adapter next to `rb.toml` imports without `PYTHONPATH`: the project directory and `[adapter] model_code` are on `sys.path` when `rb` loads a `module=` adapter, and a missing adapter module gets a fix that says where the file may live. `rabbit_brain.adapters` exports everything an adapter needs (`Case`, `Prediction`, `Metric`, `RBError`, `read_case_selector`).
  - AGENTS.md's "Custom adapters" section is now a complete, runnable adapter for a model whose forward applies an update module per iteration (loading, cases honouring `[dataset] cases`, the hook, the metric, the reference path through the team's own `eval.py`, evidence readers, the `architectures` label convention) plus what the recorder stores (mean per-pixel L2 norm of the update, times `trajectory_scale`) and how the last third and last quarter are counted. `tests/test_docs.py` runs that exact block against a toy model, so the documented adapter cannot drift from a working one.
  - `rb init` for a custom adapter no longer writes the RAFT-only keys; `rb doctor` prints small parameter counts as numbers ("3,779 parameters"), its JSON carries the failing check's code in `errors` (`E_DOCTOR` when no more specific code applies), and `rb run` announces how many evidence sheets it is about to render. `rb verify-hook` without `--checkpoint` on a non-raft adapter says what to pass.
  - Wording: a late share within a point of the limit is printed with one decimal ("25.3% ... above your 25% limit"); reversals at the limit are said to be within it; `rb check run` labels rows IMPROVED / OK / REGRESSION / NO GT instead of OK for everything that did not regress.
  - `pip install "rabbit-brain[evidence]"` (numpy and pillow) for evidence sheets with a custom adapter.
- Borderline outcomes. A case is borderline when moving one limit by a tenth (one reversal, for the reversal limit) would change what the case is called; `bundle.json` and the queue carry `borderline` (the limits in question), the findings table and the report's stability column mark it, the summary counts it, and the `why` text says which way it could go ("Borderline: a tenth of the limit either way on the late-movement limit changes this, so the same checkpoints on another GPU or torch build may call it settled instead"). It changes no definition, no verdict and no number. The reason it exists: the three RAFT example reviews were re-run on a second machine (RTX 4090 / torch 2.8 against the A5000 / torch 2.4 of the committed runs). Adapter agreement was exact on all four checkpoints and the error review reproduced case for case, but 53 of 200 cases differed by more than 0.01 px and six changed what they were called, all of them sitting within 0.04 px of a 0.3 px limit. The rule marks all six from the first machine's numbers alone, without knowing the second machine's, and AGENTS.md now tells a human re-running a review which differences are the machine and which are worth chasing. A report whose `rb` version differs from the run's now says so in its header ("Report rendered by rb X from this run's bundle.json and record.json; the numbers are the run's, the wording and any later annotations are this version's"), and the four `examples/raft-kitti` reports were re-rendered on that basis so the marks are readable on the repository page; their `bundle.json`, `record.json` and `findings.json` are untouched, so `rb report <run>` reproduces the committed report.
- `docs/experiment.md`: the pre-registered agent-baseline experiment (prompts, operator rules, rubric, predictions, decision rule) with the pilot results and the amendments they caused, committed before the counted runs.
- `llms.txt` at the repository root (and on the site): what the tool is, the one prompt, and where AGENTS.md is, for agents that look for it.
- `rb share <run>`: writes `rb-runs/<run>/share.json`, the run's anonymised statistics for the calibration corpus (task, metric, adapter id and architecture labels, iterations, environment versions, limits, per case the errors, trajectories, stability and convergence statistics, flags and outcomes with cases numbered, and the summary), prints what is in it and what is not (no case ids or names, tags, notes, paths, dataset or checkpoint names and hashes, project name, command line, evidence or verdict text), and says how the human can send it. Nothing is sent by the tool. `rb schema share` prints the schema; AGENTS.md says an agent may write the file and never sends it.

## 0.2.0 (2026-09-19): the runner
- `rb init` (rb.toml; `--demo` for a synthetic project), `rb doctor`, `rb verify-hook`, `rb run --baseline A --candidate B`.
- Adapters: `raft` (princeton-vl/RAFT and forks; KITTI-style datasets; trajectory via a forward hook on `update_block`, no code change; per-case EPE over valid pixels; unlabeled cases supported) and `synthetic` (test double); custom adapters as `package.module:Class`.
- `record.json` for runs: checkpoint sha256s, model-code git SHA, dataset hash, seeds, environment (torch/cuda/gpu), hook status, skipped cases.
- Unlabeled cases: error "not measured", stability still assessed; never counted as regressions or as passing on error.
- `TrajectoryRecorder.attach()` / `attached()` forward-hook helpers.
- Evidence rendering: `rb run` writes `rb-runs/<run>/evidence/<case>/` for the top flagged cases (`[evidence] level`, `top`; `--evidence none|standard|full`) and `rb case <run> <id> --render` for any case: the inputs and where the two models disagree (label-free), current | candidate | ground-truth flow on one colour scale, per-pixel error maps over the dimmed input and the change in error (red worse, blue better), per-iteration filmstrips for both models on one colour scale with the last quarter framed, the trajectory plot on a log axis, and `case.png` with the finding as caption. Scales are robust (flow: 95th percentile with square-root saturation; heat maps: 99th percentile capped at four times the mean) and every label states them; they were set on the real KITTI runs, where a single near pole had been dictating every scale. The re-run's numbers are checked against the run's and the result is written in the caption and the JSON. Needs numpy and pillow (`E_EVIDENCE_DEPS`); adapters opt in with `read_images` / `read_gt` (the raft adapter does).
- Trajectory regression, paired and label-free: a case is flagged (`trajectory_regression`, counts as unstable) when the candidate's late movement (mean update over the last quarter of iterations) exceeds the current model's on the same case by more than `max_trajectory_regression`. `rb init` sets it to `max_regression`; off for `rb import` unless passed. On the RAFT runs it ranks the worst error regressions first and flags nothing on candidates that settled better than the baseline; on unlabeled cases it is the regression test. `late_update_change` is in every case and queue item.
- The paper's convergence statistics, per case and label-free: from every trajectory `last_update`, `late_update`, `early_update`, `late_to_early` (quarter windows, absolute magnitudes); from a run's update fields `sign_reversal_rate` (cosine between consecutive updates below zero), `mean_cos`, `displacement_mean/max/initial` (distance of intermediate estimates from the final one) and `update_energy`. The recorder now averages the per-pixel L2 norm of the update (was L1) and takes a `scale`; the raft adapter sets 8, so RAFT trajectories are in image pixels (delta_flow is at 1/8 resolution). Late share and reversals are unchanged. New optional limit `max_last_update` (`--max-last-update`), off by default; run reports end with a per-model distribution table of the statistics.
- Receipts on real runs: the report says the run evaluated both checkpoints (not "imported"), names torch, CUDA, GPU and the model-code commit, and caps the table at every flagged case plus the top of the queue (40 rows minimum) instead of printing all 200 cases.
- The raft adapter reads each checkpoint's architecture (raft or raft-small) from its keys, so one run can compare raft-things with raft-small; the receipt lists the architecture per checkpoint. `examples/raft-kitti/runpod.sh` runs the official RAFT checkpoints on KITTI-2015 on a GPU pod.
- Real runs in the repository: `examples/raft-kitti/` holds four reviews of the official RAFT checkpoints on KITTI-2015 (receipts, findings, three evidence sheets) and the script that reproduces them.
- Releases are built and published by GitHub Actions from a `v*` tag (trusted publishing, no token); `.github/workflows/tests.yml` runs the suite on every push.
- Not yet: `rb rerun`, `rb open`, MCP.
