# The Rust core: how it is built and held

The core of rb is Rust: the binary is rb, held byte for byte to the stored expectations described under "The oracle"
(the same commands, the same output, the same bytes in `.rb/`). rb's Python package is what a script and the user's
screen need: the SDK and the terminal UI, which ask the binary for everything.

Format 1 is read whole, including the fields older writers left in it.

## Layout

- `src/sys.rs`: what differs between Linux, macOS and Windows, and nothing else does (see "Three systems").
- `src/value.rs`: Python's JSON-able values (`Value`, `Dict` = insertion-ordered), with Python's `==`.
- `src/pyfloat.rs`, `src/pyjson.rs`: `repr(float)`, the format-spec mini-language, `round`, `float()`/`int()` of text;
  `json.dumps`/`json.loads` with Python's options and error messages; `str()`/`repr()` of values.
- `src/pytime.rs`: times as rb writes them; `datetime.fromisoformat`. `RB_TEST_NOW` fixes the clock.
- `src/rng.rs`: id randomness. `RB_TEST_SEED` makes it a deterministic stream.
- `src/rbyaml.rs`: Rabbit Brain YAML, held to the reference reader `tests/rbyaml.py` (see "The oracle").
- `src/argparse.rs` + `src/cli_spec.json`: Python's argparse, driven by the command line as it is declared
  (`src/cli_parser.py`, an argparse tree; `gen/gen_cli_spec.py` writes it out). Help and usage text are argparse's own.
  `--version` says the binary's own version: the spec leaves the place open.
- `src/model.rs`: pydantic v2's validation (lax conversions, strict unions, constraint errors, messages).
- `src/record_gen.rs` (generated by `gen/gen_record.py`) + `src/record.rs`: the record models, their validators
  (`hooks`), `stored()`, `ordered()`, `new_uid`, the models' methods.
- `src/cli.rs`: `_main`: parse, dispatch, the envelope, errors. `src/commands.rs`: the registry, by the name the
  declared command line gives each command (`func`); every declared command is in it, which a test holds.
- `src/schemas.json`: `rb schema <name>` outputs (`gen/gen_schemas.py`): the record shapes from the pydantic models
  (`src/rabbit_brain/record.py`, `models.py`), the vocabulary from `src/ir.py`.
- `src/assets/mcp.json`: what `rb mcp` says of itself (`gen/gen_mcp.py`), from `src/mcp_tools.py` (the tools, the
  instructions, the resources), `src/ir.py` and the format's schema.
- `src/bridge.rs`: `rb bridge`, what rb's Python package asks rb through: one JSON request a line on standard input
  (`{"op", "root", "via", "agent", "words", "args"}`), one answer a line on standard output (`{"ok", "value"}` or
  `{"ok": false, "error"}`). An op is one call of the SDK (`add_run`, `set_setting`, `finding`, ...) or one view of
  the user's screen (`home`, `card`, `object_card`), done through the same ledger as every command. It is in no help
  text. `src/rabbit_brain/_rb.py` is its only caller: `sdk.py` and `tui.py` hold no rules of their own.

## Conventions

- Names keep their Python spelling (`_where` is `where_`, `all` is `all_kind`) and the order of operations is kept
  (floats are not associative); keep the messages byte for byte: what is stored holds them.
- Python's `str` is code points: index with `chars()`, count with `chars().count()`.
- Python's `re` and Rust's `regex` differ on lookarounds: use `fancy_regex` for those patterns only.
- No em dashes anywhere.
- Every failure is said one way: `rb <command>: <what happened>`, then `  → <what to do>` (a command line that does
  not parse shows argparse's usage first, and no fix line); with `--json`, the same in `errors[]`. No failure is worded
  as a crash: no traceback, no exception's name, no error number in brackets
  (`tests/test_failures.py` holds each kind, and scans this source for such words). `src/errors.rs` has the three
  that are not a command's own to word: `RBError::could_not_write` and `could_not_read` (a file, with the system's
  own words for why, from `sys::os_words`), and `RBError::fault` (rb's own code did not expect it: `E_INTERNAL`, exit
  3). Exit 3 is that and an install that cannot run a part of rb (the screen without its Python); a tour that stops
  exits as the step that stopped it did; every other failure is exit 2. `cli::guarded` turns a panic into that fault,
  so it is said the same way, with its envelope: each command line (also one rb runs in itself), each command, each
  request to the bridge, to `rb mcp` and to `rb open` runs under it.

## Speed: what is kept, and for how long

Speed comes from reading and working things out once. Each cache names the thing it depends on, and none changes what
a command prints:

- **For the life of the process** (safe in `rb mcp`, which lives long): a file's parse and its entries, by the file's
  time, size and inode (`DOCS`, `ENTRIES`); a record of a one-file kind as validated, by the same key (`VALID`); each
  constraint's compiled pattern (`model::regex_for`, the same `Regex` every time: a clone starts a matching cache of its
  own).
- **For one state of the record** (the index `where_()` returns; any write or a lock taken drops it): every record of a
  kind (`all`), one record (`load_cached`), the standing runs, each criterion's finding (for the criterion as given;
  dropped at a log line too), what was edited outside rb (dropped at a log line too).
- **From a command to its rb_delta**: the command's ledger hands what it worked out to the ledger rb_delta opens right
  after (`Drop for Ledger`, `Ledger::open_continuing`), when it holds the whole log as it stands. `cli::run` forgets it
  before every command line, so nothing crosses from one command, or one MCP tool call, to the next.
- **For one command line**: what git answered to a question whose answer cannot change while the command runs (where
  the repository is, what HEAD is, what a commit holds: `sources::git_bytes`, `holds`). Starting git costs a few
  milliseconds on Linux and tens on Windows. Only an answer is kept, never "no repository" or "no commit yet";
  `forget_git` drops them with everything else a command line worked out, after a watched command (it may have
  committed) and after rb makes a repository itself.
- mimalloc is the allocator: rb builds a record out of many small values.

`[profile.profiling]` builds a release binary with symbols; `valgrind --tool=callgrind` on it shows where a command
spends its time.

## What is declared, and what is written from it

Five files the binary is built from are written by a generator in `gen/`, each from a declaration someone edits:

| the binary carries | written by | from |
| --- | --- | --- |
| `src/cli_spec.json` | `gen_cli_spec.py` | `src/cli_parser.py`: the command line, as an argparse tree |
| `src/schemas.json` | `gen_schemas.py` | `src/rabbit_brain/record.py` and `models.py` (the record's shapes), `src/ir.py` (the vocabulary) |
| `src/assets/mcp.json` | `gen_mcp.py` | `src/mcp_tools.py` (the tools), `src/ir.py`, the format's schema |
| `src/errors_table.rs` | `gen_errors.py` | `src/rabbit_brain/errors.py`: the error codes |
| `src/record_gen.rs` | `gen_record.py` | `src/rabbit_brain/record.py`: the record models |

`tests/test_generated.py` fails when one of the five is not what its generator gives now, so a declaration cannot be
changed and left unwritten. The page's stylesheet and icon (`src/page_assets.rs`), the bundle's README
(`src/assets/export_readme.txt`) and rb open's shell (`src/shell/`) are edited where they are.

`THIRD-PARTY-NOTICES`, the licenses of the crates built into rb that every wheel and the sdist carry, is written by
`gen/gen_notices.py` from `Cargo.lock` with cargo-about (`gen/about.toml`, `gen/about.hbs`). It names the digest of the
lock it was written from, and `tests/test_release_setup.py` fails when the dependencies have changed since.

## Three systems

rb is the same program on Linux, macOS and Windows. What differs is in `src/sys.rs`, one function per difference
with a Unix and a Windows form: a file's stamp (time, size, and the inode or the file's index on its volume), the
record's lock (`File::lock`: flock, or LockFileEx), replacing a file (on Windows tried again for two seconds while
another program holds it), the user's home and settings directory (`%USERPROFILE%`, `%APPDATA%\rabbit-brain`), the
credentials file (mode 0600, or the profile's own permissions), what a system error says (the system's own words and
no code: `No such file or directory`, on Windows `The system cannot find the file specified`), the terminal's width,
Ctrl-C.

- **Paths are written with `/`** on every system, in the record and in what rb prints (`sys::slashed`): a record made
  on one system reads on another, a path rb prints can be pasted into any shell (a backslash is an escape in the one
  most agents use on Windows), and git writes them the same way there. A path someone types with `\` is read as the
  same path (`sys::typed`, `cmds::pathlib_str`). `sys::canonicalize` gives `C:/work`, never `\\?\C:\work`.
- **Lines end in `\n`** in everything rb writes. `.rb/.gitattributes` (`* -text`) tells git to leave the record's
  files as they are; the record reads the same with `\r\n` in it (its hashes are of content, not of bytes). A git
  set to convert line endings, as Git for Windows is by default, checks the repository's other text files out with
  `\r\n`: the same text with the other line ending is the same file wherever rb compares a file with a digest it
  recorded (`sources::is_file_of`: a setting's source, a run's files, a resource's copy, a manifest's sources, an
  indexed folder), so a checkout there does not read as a repository where everything changed, and what is recorded
  there does not flip the record for the next user (`tests/test_line_endings.py`). The digest recorded is always of
  the bytes where it was recorded.
- **A watched command** (`rb journal run`) gets a terminal of its own on Linux and macOS when rb's output is one; on
  Windows it writes to a pipe (a Python there is asked for UTF-8 with PYTHONIOENCODING unless the user chose), and
  its name is found as a shell finds it (`sys::find_program`: `.cmd` and `.bat` on PATH, which Windows alone starts
  only as `.exe`).
- **The Python beside rb**: on Windows `python.exe` beside `rb.exe` (a virtual environment's `Scripts\`) or one
  folder up; the screen's Python runs with PYTHONUTF8. The package starts rb without a console window when the
  Python has none (`_rb.QUIET`), so none flashes up in a notebook.
- **`rabbit-brain`** becomes rb on Linux and macOS (exec) and runs it as a child on Windows.

How Windows is held: the `windows` job in `.github/workflows/tests.yml` builds the binary there (MSVC) and runs
`cargo test` and the suite, and the release workflow tests the Windows wheel before anything is published. The
goldens are held on Linux alone: they carry Linux's words for a system error, and some scenarios name POSIX paths.

## The oracle

- Unit-level differential tests (`tests_py/`), the binary's own code against a second implementation:
  - `diff_numbers.py`: floats, formats, rounding, against CPython itself (400k cases);
  - `diff_argparse.py`: namespaces, usage errors, help text for every parser, against CPython's argparse on the
    command line as declared (`src/cli_parser.py`);
  - `diff_stats.py`: the statistics behind a finding, against `tests_py/reference.py` and CPython's `statistics`;
  - `diff_pyyaml.py`: a project's YAML configs, against PyYAML with rb's loader (`tests_py/reference.py`);
  - `diff_yaml.py`: rbyaml load, comments, canonical form, errors, against the reference reader (156k cases with
    mutations);
  - `diff_records.py`: validation errors and stored forms on the suite's own records plus mutations, against the
    pydantic models (115k cases).
  Build the helper with `cargo build --release --features oracle` (it is never shipped), then run each as
  `python3 tests_py/<name>.py target/release/rbdiff [args]`.
- The suite, `tests/`: every test drives rb from outside, through `tests/rbtest.py`. `main` is the command line; the
  record is read through the SDK (`state()`) and the screen's views (`home()`, `object_card()`, `found_card()`), which
  ask rb; `Mcp` is an agent's connection to `rb mcp` over stdio; `Open` is `rb open` as its own process; a watched
  command gets a real terminal. It drives the rb installed beside the Python that runs it (`pip install -e .` builds
  one), or the one RB_BIN names. `tests/rbyaml.py` is the reference reader of the files, a second implementation of
  Rabbit Brain YAML in Python.
- The golden records, `python3 rust/tests_py/golden.py <binary> [scenario...]`: command scripts
  (`tests_py/golden_scenarios.py`) run with the clock, the ids, the version rb says it is and the machine a receipt
  names all fixed (`RB_TEST_NOW`, `RB_TEST_SEED`, `RB_TEST_VERSION`, `RB_TEST_ENV`), and the login and the locale with
  them; every command's exit code, stdout and stderr and every file left in the working tree are held byte for byte
  to what is stored in `tests_py/golden/<scenario>.json` (the directory a scenario ran in written `@BASE@`), in half a
  minute. `golden.py --record <binary>` stores it again after a change meant to change it: read the diff of the stored
  files before committing them, since they are then the only witness. Stored once, it holds on any machine: nothing a
  scenario writes depends on where it ran, on the filesystem's listing order, or on who ran it. The scenarios cover
  the writes, three worktrees merged into one experiment, an id minted on two branches, a record git merged from both
  sides (and one merged by hand), a removed worktree's journal, a record kept the earlier way moving to one file per
  part, what other worktrees and unmerged branches hold, every record kind read back, one whole conversation with
  `rb mcp` (every method, every tool, the malformed and the refused) and one with `rb bridge` (every op, then
  everything that is not a request). An `rbsh` step runs `$RB` through the shell, for a command line that names an id
  only rb knows. A zip is compared by its entries (names and bytes), a gzipped cache file decompressed.
  `.rb/cache/environment.json` is not compared.
- `diff_open.py <binary> [scenario...]`: `rb open` on a record it built: every route, a card for every object and
  every found item, and the requests a browser never sends but Python's `http.server` answered in its own way (other
  methods, HTTP/0.9, bad versions, absolute and doubled paths, the limits), held to what is stored
  (`tests_py/golden/open-<scenario>.json`, each distinct body once) but for the `Server` and `Date` lines. Scenario
  `found` is its own: a record with things rb found and not yet recorded. `--record <binary>` stores them again.
- `diff_hub.py <binary>`: `rb login`, `rb logout`, `rb sync` and `rb clone <address>` against one stub hub that
  answers every way the hub can, and against addresses out of reach, held to what is stored
  (`tests_py/golden/hub.json`), with the stub hub at a fixed address (127.0.0.1:47821), since the project a clone
  lands records where it came from. A failure to connect is said in the machine's own words: what is stored is
  Linux's.
- The agent contract (`bench/agent`): its cases, scripted agents and checks drive rb through `bench/agent/drive.py`
  (the command line, and the SDK for what an agent left), and a live agent gets a counting `rb` on its PATH that is
  the same rb.

A failure to connect is said in the system's own words (`Connection refused`, `Name or service not known`; a proxy
that refuses the tunnel as `Tunnel connection failed: 403 Forbidden`). On purpose, `rb open` answers a malformed
request as Python's `http.server` does. The binary's own: `rb open` says `Server: rb/<version>`, the HTTP client says
`User-Agent: rb/<version>`, verifies certificates with the platform's own verifier (rustls-platform-verifier: the
system store, SSL_CERT_FILE honoured), and says a certificate that was not accepted in a sentence of its own
(`http::certificate_words`); any other failed TLS handshake is worded as rustls words it.

## Python beside the binary

Every command runs in the binary. It runs Python for two things only: the user's screen (`rb ui`, and bare `rb` in
a terminal, check where they are and then open `rabbit_brain.tui`, drawn with textual, which asks this rb for what
it shows: RB_BIN names it), and the environment a run records (the project's Python: RB_PYTHON, else the one beside
the binary, found through a link as pipx and uv tool make them; on Windows `python.exe` beside `rb.exe` or one folder
up).

`src/rabbit_brain/` holds `_rb.py` (how the package asks rb: `rb bridge`, one process a call), `sdk.py`, `tui.py`,
`errors.py`, and `record.py` with `models.py`: the models the SDK returns, and what `gen/` writes the binary's
shapes from. Wheels (maturin, bin bindings, as uv and ruff ship) carry the binary and that package beside it.
